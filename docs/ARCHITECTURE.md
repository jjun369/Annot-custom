# Architecture

Status: Implemented for PageDock 0.4 unless marked Deferred.

```text
Electron shell
  -> loopback-only Next.js standalone server
     -> React UI (library / research / settings)
     -> legacy .annot JSON sessions, metadata, highlights
     -> node:sqlite FTS5 database (.annot/pagedock.sqlite)
     -> PDF text/image helpers
     -> Codex CLI or authenticated Codex account transport
     -> Crossref / Unpaywall / optional OpenAlex and patent services
```

Electron packages the web server and opens a desktop window. Runtime data lives in PageDock Library, never the installation directory. The local server is loopback-only. The packaged shell adds a per-process desktop token to the initial root request and scoped loopback subrequests; that token is never exposed to remote web-provider views. Existing JSON remains the compatibility layer while research relationships, chunks, projects, patents, reports, and evidence use SQLite.

The sandboxed Electron renderer exposes one narrow preload capability for choosing a library directory with the native operating-system dialog. It does not expose arbitrary filesystem, shell, credential, or process access to the web UI.

The optional DeepSeek Web Manual Bridge uses a separate Electron `persist:pagedock-deepseek-web` BrowserWindow partition with no PageDock preload, `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, and `webSecurity: true`. PageDock may explicitly copy a reviewed selection/question prompt and open `chat.deepseek.com`, but it does not inject into the page, automate send/read, inspect web storage, or handle credentials. A direct selection question is first saved as an ordinary user message in the existing PDF session; a primary AI answer is not required. A user may explicitly paste a copied response back through a local route, which reconstructs the canonical selection/question prompt from the persisted PageDock anchor before attaching additive manual-perspective metadata. Clearing the separate web session clears only that partition's site data and cache; it does not touch Library data.

The independent side-chat popup is a separate `/side-chat` renderer and Electron `BrowserWindow`; it uses `sessionKind: "sidechat"` records in the root `.annot/sessions.json` namespace and never reuses a PDF session's messages or `providerSessionId`. Its PageDock AI turn reuses the existing Codex/Claude runtimes with a temporary working directory and no implicit Library, PDF, Knowledge, or folder-tool context. A question is persisted before the optional provider call. A deliberately handed-off bounded selection keeps its `documentId`, page, normalized rectangles, text, and highlight id; its relative `sourcePdfPath` is only a navigation hint and is refreshed after a document-identity rename. An immutable `sideChatWebRequests[]` record is appended to the canonical user question before copying: imported answers bind to that stable request and cannot be reinterpreted from the current UI mode or a later assistant answer. The popup's web tabs use isolated provider-specific Electron `WebContentsView` partitions for the official DeepSeek, ChatGPT, Claude, and Gemini top-level destinations. They are never iframes, never receive the PageDock preload, and never inject, send, poll, or read remote content. A provider load/security failure opens the official URL in the system browser. User-visible prompt preview/copy and manual paste/save are the only cross-service handoff; web model labels remain explicitly unverified. The controller single-flights loads, generation-guards stale tabs, clamps bounds to the popup content area, hides views for local overlays/minimize/small hosts, and removes each view independently during cleanup.

Session JSON remains the compatibility layer for chat history and imported perspectives. Every `sessions.json` writer takes a per-file lock; mutations read the latest array inside that lock and apply a domain-specific patch, so a chat completion cannot overwrite an overlapping import or another session's update. Delete, rename/move, restore, and reconciliation writers use the same serialization boundary.

An explicit sidechat reflection is a latest-state patch on its canonical user question. It remains inside the sidechat session and is not projected into PDF records, Knowledge, cards, or any provider/web prompt; the existing session backup carries it as an optional JSON field.

PDF ingestion computes SHA-256, creates or finds a `documentId`, and keeps the current relative path plus aliases. Workspace scans repair a missing path when exactly one matching hash exists. Ambiguous matches become visible conflicts. Replacing the contents at an existing path creates a blocking `content-changed` conflict; PageDock retains the previous identity hash until the user explicitly accepts the current file as a new version.

Large PDF indexing is a process-local single-flight job. Python/PyMuPDF writes JSONL page events to stdout; Node validates the complete protocol, splits each page, and writes disposable NDJSON staging below the operating-system temp directory rather than the workspace or database directory. Before the one SQLite transaction, PageDock re-reads the document record, rechecks path/size/mtime, and verifies its SHA-256. Cancellation is accepted only before the state changes to `committing`; the transaction replaces chunks, indexed time, and FTS together, so source changes, cancellation, process restart, and commit failure leave the prior index intact. Terminal snapshots remain in process memory for 30 minutes and cannot be resumed after a restart.

Codex authentication and model selection follow the user's ChatGPT OAuth account. A standalone CLI is preferred for local, tool-enabled turns; when the OpenCodex desktop app exposes only a protected internal binary, PageDock uses the authenticated Codex account transport as a fallback. `자동` does not pin a model version. Fallback chat reuses only a bounded set of persisted messages and the explicitly supplied source context. Connection validation checks the authenticated model catalog without spending a model turn. Analysis sends only the selected document chunks and selected page images, validates returned evidence against real chunks/pages, and stores the structured report locally.

Source credentials are stored outside the library in the user's PageDock application-data directory. Windows DPAPI protects secrets. They are excluded from backup and logs. Historical macOS Keychain compatibility code is not part of the supported release contract and may be removed during later maintenance.

PageDock packages and releases only Windows 10/11 x64 through NSIS. Build verification, smoke testing, code signing, updates, and installer-size work target Windows only. The abandoned experimental Apple Silicon port is retained only as repository history; no Mac artifact is supported or distributed.

Backups use a v2 manifest. PDFs and legacy JSON are ordinary archive files; SQLite is exported to normalized research JSON and merged during restore. v1 import remains supported. Restore first creates a metadata-only safety snapshot. Python performs streaming extraction when available; archives up to 512MB also have an in-process fallback so a fresh friend PC is not blocked before PDF-tool setup.

## Mobile bridge

The device-local `%APPDATA%\\PageDock\\mobile-bridge.json` stores only an optional external bridge path, a stable-document-id Mobile Shelf, and additive operational publication state (opt-in automatic-publication preference, dirty/revision markers, last successful publish, and bounded retry metadata). It is operational device state, not Library data and not a portable backup input. A bridge has `Mobile`, reserved `Inbox`, `Backups/Manual`, and `Backups/Auto` directories. `PageDock-Mobile.pdf` plus a tiny SHA-256 receipt is a disposable phone projection; it is generated with selectable text and in-memory visual-region renders. The original PDF, SQLite, `.annot`, sessions, and Knowledge store never become live bridge files.

Automatic v2 backups are first written as a local partial archive, reopened and checked against their manifest, then published as a local success. A configured bridge receives a byte-identical copy only afterwards. Each location prunes its own successful automatic ZIPs to three; manual bridge archives include PDFs and are never pruned. A mobile-PDF receipt mismatch is a conflict: PageDock preserves a user-approved modified pair in `Mobile/Conflicts` rather than importing or silently overwriting it.

Deferred: WebView2 shell, embeddings/vector database, cloud sync, and company AI adapters.

## PDF study-loop persistence

The Reader keeps its existing native-PDF plus `.annot` sidecar annotation strategy. Semantic study fields are optional sidecar metadata and are merged with native annotations without changing the native PDF payload. Existing session JSON stores optional, bounded source context for user/assistant turns; the trusted chat route validates it before a provider sees it. Paper metadata stores a portable reading position, while the route skips FTS refresh for reading-only updates. These three JSON stores remain ordinary portable-backup inputs and do not require a SQLite migration.

Source-Anchored Recall cards are optional `study.cards` data inside that same annotation sidecar. Basic cards keep editable front/back text. A manual Cloze additionally stores `kind: "cloze"` and one validated exact-text span (`clozeText`, `clozeStart`, `clozeEnd`) into its immutable selection source; the Reader derives the blank at render time rather than mutating the source or adding an Anki-style markup format. Cards reuse `ChatSourceContext` for `documentId`/page/rect/text anchoring and keep only the latest minimal review state. `review.nextReviewDate` is one optional local calendar date (`YYYY-MM-DD`): a current-PDF queue treats missing legacy dates and dates on/before today as due, while `again` writes tomorrow and `remembered` writes three calendar days later. The same sidecar may carry optional `Highlight.workKind` and `workDoneAt` for Reader-local Evidence → Work Item state; the original rect/text anchor and existing note remain canonical, and the server bypasses native-PDF/Python updates for work-only changes. `읽기 기록`, the Evidence Brief preview, and the Library's small resume/count line are projections of these existing highlights plus `PaperMetadata.readingPosition`; none is a second task or study store. The sidecar writer serializes highlight and card mutations through one atomic per-sidecar path, so card actions cannot silently overwrite a concurrent highlight update. SQLite remains a future rebuildable index candidate, never the canonical study record.

## Personal knowledge flow

The knowledge area stores its active versioned JSON at `.annot/knowledge-store.json` and recoverable removed history at `.annot/knowledge-revision-trash.json`. Capture is local and immutable. A Reader highlight or AI answer may be promoted into the same inbox with an explicit provenance class and its existing bounded source anchor; it is never directly written to the wiki. A deterministic term matcher selects bounded, visibly marked head/tail excerpts from candidate topics. Codex returns schema-constrained proposals in a cancellable, time-bounded read-only process, and application code applies only proposals explicitly accepted by the user. Direct user edits also create revisions without a model call. A manual topic review creates only an attention timestamp, never a revision. A v1 source is preserved as a verified content-addressed rollback file before the first mutation; active and trash JSON files use validated temporary writes and atomic rename.

The 0.4.4 knowledge capture extension keeps its folder path and bounded file fingerprint ledger in device-local `%APPDATA%\\PageDock\\knowledge-import.json`. Folder scans are explicit on knowledge-page entry or refresh, recurse through ordinary subdirectories, skip symlinks and known runtime/export directories, and read only UTF-8 text files. Long-file segmentation is a deterministic local operation before normal inbox capture. Markdown export writes only the current topic projection to a timestamped destination through a temporary directory and never writes inside the configured import folder.

The shared `AppHeader` opens static screen-aware help content by button or `F1`; it does not load external documentation at runtime.
